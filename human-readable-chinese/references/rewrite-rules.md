# 改写手术：R1 ~ R11

按顺序执行。R1~R7 改结构，R8 改理解门槛，R9~R11 改可信度。

---

## R1 主干先行：先写「谁 + 做了什么 + 对象」，修饰语全部后置

```
坏：本次针对批量导出场景下异步任务超时缺乏兜底机制的问题的修复，已在 v2.3 上线。
好：v2.3 修了一个问题：批量导出时异步任务会超时，之前没有兜底。
```

先落地主干，再补条件。**不要在一句话的开头就挂一串「针对……的……」。**

---

## R2 主谓相邻：主语到谓语 ≤ 8 字，中间不插逗号

需要补条件时，把它挪到主干之后，或独立成句。

```
坏：首页在弱网环境下首次加载且本地无缓存时出现的白屏，在预加载上线后消失了。
好：首页白屏的问题没了。触发条件是弱网 + 首次加载 + 本地无缓存；预加载上线后就没再出现。
```

---

## R3 一句一主干，句长 15~35 字

超过 40 字必拆。**但拆句时必须补连接词**（因为/所以/但是/如果），不能拆成互不相干的两句——那是「机械断句」，读者要自己补逻辑。

```
坏（拆错）：导出失败。用户重试。还是失败。
好：导出失败后用户重试，仍然失败，原因是任务队列满了。
```

---

## R4 主语必须能做出那个动作

三选一：换成有生主语（人/团队/系统/服务/脚本）／换成被动或「把」字句／换成「因为……所以……」的因果句。

```
坏：这次重构让订单链路的可维护性获得了呼吸的空间。
好：重构之后，改订单模块的代码不用再动另外三个文件。
```

> **边界**：「系统/服务/脚本/接口」可以当主语（它们确实在做事，如「服务返回 500」）；「体系/链路/能力/维度/抓手/生态」不行（它们做不了事）。

---

## R5 动作还给动词，砍掉空壳

「进行优化」→「改快」；「实现下降」→「从 8 秒降到 2 秒」；「开展排查」→「查了」。

```
坏：对导出性能进行了优化，实现了响应时长的显著下降。
好：导出从 8 秒降到 2 秒。
```

**能写数字就写数字。** 抽象形容（显著/大幅/有效/明显/充分）是 AI 味的重灾区；写了就必须跟数字或具体事实。

---

## R6 定语超两个「的」就拆出去

把最长的定语提出来单独成句，或改成后置的补充说明。

```
坏：一个基于埋点数据、面向新用户、支持多策略切换的冷启动配置校验逻辑
好：冷启动配置多了一个校验。它读埋点数据，只对新用户生效，支持在多个策略间切换。
```

---

## R7 显式连接：把「——」和并列空转换成因果/条件/转折

```
坏：数据量涨了十倍——批处理没改——结果就是每天延迟两小时。
好：数据量涨了十倍，但批处理逻辑没跟着改，所以每天的任务延迟两小时。
```

---

## R8 术语首现就地解释（内嵌同位语）

不要留缩写给读者猜。第一次出现时，紧邻位置垫半句大白话。

```
坏：冷启动阶段依赖 CF 召回，存在稀疏性问题。
好：新用户没有历史行为（冷启动），只能靠协同过滤（CF，看「和你相似的人喜欢什么」）来推荐；
    但这种情况数据太少，推荐不准。
```

---

## R9 保真：原子命题一个都不许丢

改写只动**包装**，不动**事实**。数值、单位、条件、边界、例外、时间点，逐项核对留痕。

为读起来顺而删掉限定条件，是最严重的失败——比难读严重得多。

---

## R10 数字必须能指回出处

**精确的数字比模糊的形容更危险**，因为读者会信它。

- 写之前问一句：这个数字从哪来的？能指出原文哪一句吗？
- 原文只说「半秒」，就不要写「200 毫秒」。**精度不能靠脑补。**
- 转述别人的结论时，先分清那条结论测的是**认知负荷**、**阅读时间**还是**答题准确率**。这三个常被二手文章混着用，混了就是把别人的结论改强了。
- 拿不准时降级成区间或定性表述（「大概几百毫秒」「明显变慢」），并标明这是估计。

---

## R11 比喻配额：一段最多一个

比喻只能**解释**事实，不能**代替**事实。

```
坏：模型把减速带全拆了，所以读起来像压缩饼干；读者像在搬水泥袋。
好：模型删掉了这类缓冲词。结果是每句话的局部信息更密，读起来更费脑。
```

写完数一遍：这段有几个比喻？超过一个，删到只剩最准的那个。

**最危险的写法，是用比喻把没说清的地方盖过去**——读者觉得懂了，其实没懂。
